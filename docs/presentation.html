The Problem

Business Users Cannot Access Their Own Data

🔐

Cryptic Internal Codes

The metrics DB stores status='A', region='DFW', outcome_code='3' — meaningless to business users without a lookup table.

⏳

Multi-Day Turnaround

Every ad-hoc question requires an engineer to decode the business intent, find the right tables, write SQL, and format results. Average wait: 1–3 business days.

🚧

Engineering Bottleneck

30–40% of engineering time is spent answering analyst queries. This blocks product work and creates a single point of failure when the "SQL expert" is on leave.

📊

Rigid Dashboards

Pre-built dashboards cannot handle ad-hoc questions. Every new business question requires a new dashboard — a weeks-long engineering project.

The Solution

Three Intelligence Layers Between User and Data

Layer 1 — Schema Intelligence

Schema Registry knows every table, column, and internal code. Value Mapper translates "Dallas" → 'DFW' before SQL is ever generated. The model never needs to guess.

Layer 2 — Query Intelligence

Local AI (Ollama + SQLCoder) generates SQL from an enriched prompt containing the schema DDL, value hints, and the user question. A safety validator blocks any non-read operations.

Layer 3 — Report Intelligence

A second local AI call (Mistral) converts raw result rows into a narrative report with a summary, key insights, and recommended actions.

-- User types (plain English):
"active Enterprise customers in Dallas"

↓ Layer 1: Schema Intelligence
active   → status = 'A'
Enterprise → segment = 'ENT'
Dallas   → region = 'DFW'

↓ Layer 2: Query Intelligence (Ollama)
SELECT COUNT(*) FROM customer_accounts
WHERE status = 'A'
  AND segment = 'ENT'
  AND region = 'DFW'
LIMIT 10000  -- auto-injected

↓ Layer 3: Report Intelligence (Ollama)
"There are 10 active Enterprise customers
in the DFW region, representing $20,362
in monthly recurring revenue..."

Module 2 — Table Retrieval

How the System Finds the Right Tables

With 200+ tables in a telecom metrics server, passing all schemas to the AI would exceed the model's context window and reduce accuracy. The retriever narrows it to 2–3 tables per query.

+10
Table name matches query term
"orders" in query → orders table scores +10
+5
Table keyword matches query term
Table tagged "billing" → matches "invoice" query
+3
Column name appears in query
"region" column → "Dallas region" query
+4
Value human_label in query
"Active" label → "active customers" query

Phase 2 Upgrade

Replace keyword scoring with local sentence-transformer embeddings for semantic matching — handles synonyms and paraphrasing. Drop-in replacement, same interface.

Module 5 — SQL Validator

5-Rule Safety Net Before Any Query Runs

Uses sqlglot AST parsing — not regex — to guarantee safety at the syntax tree level. If validation fails, the pipeline retries with error feedback to the SQL Generator (max 2 retries).

#RuleWhat It BlocksOn Failure
1 Read-Only Enforcement INSERT, UPDATE, DELETE, DROP, CREATE, ALTER, TRUNCATE Reject
2 Table Whitelist Any table not in config/table_whitelist.py Reject
3 Row Cap LIMIT > 10,000 rows. Auto-injects LIMIT if missing. Inject / Reject
4 Subquery Depth Nested subqueries deeper than 3 levels Reject
5 Set Operations UNION / INTERSECT / EXCEPT (unless explicitly enabled) Reject
6 Execution Timeout Queries running longer than 30 seconds Kill
49/49 tests passing  —  All 6 rules covered by automated tests in tests/test_sql_validator.py, including read-only enforcement, whitelist, limit injection, subquery depth, and set-operation blocking.

Enterprise Compliance

Meets Enterprise Security & Compliance Requirements

Data Privacy

100% on-premise. No data leaves the enterprise network. No cloud LLM API calls. Passes data residency requirements for telecom, finance, and healthcare regulations.

Authentication & RBAC

JWT tokens on every endpoint. Role-based access: Analysts run queries, Admins view the full audit trail. Password hashing with PBKDF2-SHA256 (260K iterations).

Immutable Audit Trail

Every query logged: user ID, timestamp, original question, generated SQL, tables used, row count, execution time, and status. Admin-only access to the audit endpoint.

SQL Safety

AST-level parsing via sqlglot. 5 validation rules block all write operations, unauthorized tables, oversized queries, and deep subqueries — before any DB execution.

Schema Freshness

Auto-scanner discovers new tables/values from the live DB. Nightly delta detector flags unknown values and emails the data team — nothing silently breaks.

Rate Limiting

20 requests/minute per IP (configurable). Prevents runaway batch abuse. Backed by slowapi — Redis storage in multi-worker production deployments.

Deployment

Running in 6 Commands

# Step 1 — Install Ollama + pull models
curl -fsSL https://ollama.com/install.sh | sh
ollama pull sqlcoder
ollama pull mistral

# Step 2 — Clone & configure
git clone <your-repo>/Text-to-Insights
cd Text-to-Insights
cp .env.example .env
# edit .env → set your metrics DB URL

# Step 3 — Install Python deps
pip install -r requirements.txt

# Step 4 — Seed the registry
python -m scripts.seed_telecom

# Step 5 — Start API
uvicorn api.main:app --reload

# Step 6 — Start UI
streamlit run ui/app.py

# OR run everything with Docker:
docker compose up -d
docker exec tti-ollama ollama pull sqlcoder
docker exec tti-ollama ollama pull mistral
